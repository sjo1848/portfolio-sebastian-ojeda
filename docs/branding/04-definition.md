# Branding — Definition

Status: **DEFINITION / candidate PASS**
Issue: #63
Input: Discovery PASS + Critic conditions C1–C7

## 1. Brand objective

Create a personal portfolio identity that is memorable enough to distinguish Sebastián from a generic developer template while remaining immediately legible to recruiters and technical hiring teams.

Branding must strengthen the existing portfolio hierarchy:

1. understand who Sebastián is;
2. understand what kind of software he builds;
3. inspect selected project evidence;
4. understand how he works;
5. contact him or inspect code.

## 2. Audience hierarchy

### Primary
**Recruiters, hiring managers and technical leads evaluating Full-Stack / Backend / software engineering profiles.**

What they need in the first pass:
- explicit professional category;
- evidence of end-to-end capability;
- project maturity and role;
- technical depth without reading everything;
- clear path to case studies, GitHub and contact.

### Secondary
**Potential clients, collaborators and technical peers** evaluating whether Sebastián can understand a real workflow and turn it into reliable software.

### Not primary
- buyers of a FALDEO agency/studio;
- SAP-only audiences;
- mining-only audiences;
- an AI-agent-methodology audience.

Those contexts may reinforce credibility but cannot replace the software-engineering identity.

## 3. Positioning architecture

### Brand owner
**Sebastián Ojeda**

### Role anchor
**Full-Stack Software Developer**

This remains explicit for recruiter classification and searchability.

### Differentiation territory
**End-to-end software for real operational workflows.**

Spanish working proposition:

> **Convierto procesos reales en software end-to-end verificable.**

English working proposition:

> **I turn real-world workflows into verifiable end-to-end software.**

This is a positioning contract, not yet final hero copy. DESIGN may refine wording without changing its meaning.

### Supporting proof areas
- backend and domain modeling;
- web/mobile interfaces;
- data and integrations;
- cloud/deployment/quality;
- applied AI and automation when they add concrete value;
- operational context and traceability.

### Credibility mechanism
**Evidence over adjectives.**

Claims should resolve into at least one of:
- working product behavior;
- screenshot / walkthrough;
- repository;
- architecture or implementation detail;
- tests / CI / QA;
- explicit project state and limitations;
- professional experience.

## 4. Desired first-10-second understanding

A new visitor should be able to answer:

1. **Who?** Sebastián Ojeda.
2. **What role?** Full-Stack Software Developer.
3. **What is different?** He builds complete systems around real workflows, not isolated interfaces.
4. **Where is the proof?** Selected product/engineering case studies with visible evidence.

If branding makes any of these harder, it fails.

## 5. Brand personality

### Precise
Uses concrete language, explicit states and evidence.

### Practical
Shows systems solving actual workflow problems rather than conceptual demos alone.

### Systems-minded
Connects interfaces, backend, data, integrations, authority, QA and operations.

### Calm technical
Feels engineered and confident without cyber aesthetics, hype or visual aggression.

### Human-authored
Feels intentionally made by Sebastián; not a generic template and not an AI-generated design language.

## 6. Verbal system

### Preferred language
- build / construir
- system / sistema
- workflow / flujo
- evidence / evidencia
- verify / verificar
- operate / operar
- integrate / integrar
- decisions / decisiones
- constraints / restricciones

### Avoid
- passionate developer
- innovative solutions
- cutting-edge without proof
- next-generation
- seamless experiences as generic filler
- expert / senior unless contextually supported
- transformation language without a concrete before/after

### Sentence style
- short declarative headlines;
- active verbs;
- one idea per sentence where possible;
- technical detail progressively disclosed;
- no gratuitous English inside Spanish pages unless it is a defined product/technical term.

## 7. Visual brand contract

Exact execution belongs to DESIGN. The following principles are fixed.

### 7.1 Light-first, warm-neutral foundation
The current stone / off-white canvas is a strong base and should be preserved unless a Design experiment proves a material improvement.

### 7.2 Ink as structural contrast
Dark ink/night tones should carry text, technical frames and high-contrast sections rather than turning the entire portfolio into a dark developer theme.

### 7.3 Copper/rust as signal, not decoration
The current warm accent is distinctive enough to continue testing. It should identify actions, evidence markers or important navigation states—not appear everywhere.

### 7.4 One recurring signature motif
The final design may use one subtle motif derived from systems, routes, evidence or field/operational context. It must remain abstract.

Prohibited as dominant motifs:
- literal mountain logos;
- pickaxes/mining iconography;
- contour-map wallpaper on every section;
- circuit-board/cyber backgrounds;
- terminal/code-rain aesthetics.

### 7.5 Screenshots are product evidence
Images should be framed consistently and remain readable. Branding cannot crop or stylize them so aggressively that product evidence becomes decorative texture.

### 7.6 Typography must create hierarchy before ornament
The system should distinguish:
- identity / hero;
- section editorial headings;
- project titles;
- body reading;
- technical metadata.

A mono face/style may remain for evidence/index metadata, but not dominate body text.

## 8. Homepage information hierarchy

### Tier 1 — Identity
Name + role + differentiating proposition + primary project CTA.

### Tier 2 — Selected work
The four primary cases remain the visual center of gravity.

Required card-level information:
- project identity;
- one concise problem/solution summary;
- visual evidence when available;
- role or ownership signal;
- limited technical context;
- one obvious case-study CTA.

Information that may move deeper:
- long evidence lists;
- extensive stack lists;
- implementation detail already covered by the case study.

### Tier 3 — Capabilities / experience
Supports the project proof rather than preceding it.

### Tier 4 — Method
Project Method reinforces trust and differentiates process, but should not visually overpower selected work.

### Tier 5 — Contact
Clear, low-friction close.

## 9. Conversion objectives

Primary conversion:
**Open a selected case study.**

Secondary conversions:
- inspect GitHub/code;
- contact Sebastián;
- understand experience/capabilities;
- inspect Project Method.

The homepage should not have equal visual weight for every action.

## 10. Acceptance criteria for DESIGN

A proposed design direction can pass only if:

1. `Full-Stack Software Developer` remains explicit in the first viewport at 360, 768 and 1440 px.
2. A one-sentence differentiator is visible without requiring project-section reading.
3. Selected work is the strongest visual content after the hero.
4. Project evidence remains legible and same-origin.
5. The primary CTA hierarchy is obvious.
6. Project cards use fewer competing metadata treatments than the current baseline.
7. The identity remains coherent in ES and EN.
8. The direction does not look like a generic Tailwind/shadcn portfolio template.
9. The direction does not imitate a reference portfolio’s signature vocabulary or composition.
10. Keyboard focus, reduced motion, responsive reading order and WCAG AA contrast are preserved.
11. Lighthouse/release budgets must not regress materially during BUILD.
12. No unsupported professional claims are introduced.

## 11. Success indicators after release

Qualitative:
- role and differentiator can be summarized after a brief scan;
- selected projects feel related by one authored system;
- the portfolio has a recognizable visual voice without distracting from evidence;
- project pages and homepage feel like one brand.

Observable implementation checks:
- responsive visual matrix passes;
- no broken image/media paths;
- ES/EN parity;
- no horizontal overflow;
- focus visibility and reduced motion pass;
- release QA and Lighthouse gates remain green.

## 12. Explicit non-goals

This branding increment will not:
- rename the portfolio to FALDEO;
- add unsupported testimonials or metrics;
- redesign project applications themselves;
- add a blog/journal/archive just to resemble references;
- introduce a large logo animation;
- replace project evidence with generated illustrations;
- change the selected project set solely for visual reasons.

## 13. Handoff to DESIGN

DESIGN must produce **multiple distinct directions** against this same contract. A direction is not valid merely because it is attractive; it must explain how its typography, palette, motif, spacing, project composition and verbal hierarchy satisfy the criteria above.

No BUILD is authorized until the chosen direction passes critic/integration review and receives a Human Gate approval.
