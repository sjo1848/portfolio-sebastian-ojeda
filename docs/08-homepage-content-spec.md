# Especificación de contenido de la página principal

## Estado

Borrador completo listo para revisión editorial. El copy vive en `content/homepage.md`.

## Objetivo

Permitir que un reclutador o responsable técnico comprenda en menos de diez segundos:

1. Qué tipo de desarrollador es Sebastián.
2. Qué clase de problemas resuelve.
3. Qué proyectos lo demuestran.
4. Cómo trabaja.
5. Cómo contactarlo.

## Orden narrativo

```text
Identidad profesional
→ Evidencia mediante proyectos
→ Método de trabajo
→ Capacidades
→ Contexto operativo
→ Sobre mí
→ Contacto
```

## Hero

### Mensaje principal

**Desarrollador Full Stack con foco en Backend**

### Mensaje secundario

Desarrollo sistemas de gestión y aplicaciones operativas con Rust, TypeScript, React, React Native y PostgreSQL.

### Prueba contextual

Se menciona experiencia en sistemas empresariales, SAP e integraciones para explicar la orientación a procesos reales, sin convertir esas áreas en títulos profesionales paralelos.

### CTA

- Principal: Ver proyectos.
- Secundario: Descargar CV.
- Utilitarios: GitHub y contacto.

## Proyectos

### HMS Elite

Función narrativa: demostrar profundidad técnica y capacidad para sistemas empresariales complejos.

### GasFlow

Función narrativa: demostrar producto móvil, operación y conexión frontend/backend.

### A-M-R Refrigeración

Función narrativa: demostrar UX comercial, frontend y criterio para elegir una arquitectura simple.

## Cómo trabajo

La sección no presenta una metodología abstracta. Explica cinco decisiones observables:

1. Entender el dominio.
2. Diseñar el flujo.
3. Construir la solución.
4. Validar la calidad.
5. Preparar la operación.

## Capacidades

Las tecnologías se agrupan por capacidad y contexto. No se usarán porcentajes de dominio ni nubes extensas de logos.

## Experiencia

La experiencia SAP, integración, logística, mantenimiento y operaciones se utiliza como contexto diferenciador. No desplaza el objetivo laboral principal de desarrollo de software.

## Contacto

La sección se mantiene visible aunque algunos enlaces todavía estén pendientes. Los placeholders no llegarán a producción.

## Reglas editoriales

- No usar “experto”, “arquitecto” o “senior”.
- No afirmar uso productivo sin evidencia.
- No presentar proyectos conceptuales como implementados.
- Diferenciar estado funcional, desarrollo activo y pendientes.
- Evitar frases genéricas como “apasionado por la tecnología”.
- Priorizar verbos y evidencia concreta.
- Mantener párrafos cortos y escaneables.

## Datos bloqueantes para publicación

- Email profesional.
- LinkedIn.
- Modalidad y disponibilidad laboral.
- CV final.
- Decisión de retrato.

Estos datos están centralizados en `content/profile/public-profile-data.md`.

## Criterios de aceptación

- El título profesional aparece una sola vez como mensaje dominante.
- Los tres proyectos se diferencian por función y evidencia.
- Cada proyecto comunica su estado real.
- QA, UX y arquitectura aparecen como práctica, no como eslogan.
- El contenido puede implementarse sin inventar información adicional.
- Los únicos placeholders están centralizados y documentados.
